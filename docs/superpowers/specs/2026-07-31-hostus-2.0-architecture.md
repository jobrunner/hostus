# hostus 2.0 — Master-Architektur-Spec

**Datum:** 2026-07-31
**Status:** Entwurf zur Umsetzung (freigegeben)
**Grundlage:** `hostus-loesungsarchitektur.md` (Stand 28.07.2026), ortus-Harness-Inventar, Brainstorming-Session 2026-07-31
**Nachfolgende Dokumente:** je Sub-Projekt ein eigener Implementierungsplan (via writing-plans)

---

## 0. Zusammenfassung

hostus wird von einem zustandslosen GBIF-Autosuggest-Proxy (~2.000 LOC, ADR-001/-003/-008: kein Persistenz-Layer, GBIF als alleiniger Provider) zu einem **Multi-Backbone-Namens- und Merkmalsservice** umgebaut. Das ist eine architektonische Inversion, kein Ausbau: hostus betreibt künftig einen **lokalen, aus versionierten Artefakten gespeisten Index** und bedient sieben Endpunkte plus ein Offline-Bundle.

**Systemgrenze:** hostus 2.0 ist **ausschließlich** der Namens-/Merkmalsdienst (7 Endpunkte + Ingest-Pipeline + Offline-Bundle). Das `plant_record`-Schema (Teil D.1 des Quelldokuments), `situs` und der RDF-Knowledge-Graph (UC3) sind **externe Consumer** und liegen außerhalb. hostus bleibt read-only bezüglich Erfassungsdaten; schreibend ist nur der Ingest (Backbone-Import).

**Vorgehen (freigegeben):**
1. **Phase R** — Recherche & Quellenvalidierung (Quellenregister).
2. **Phase 0** — PoC-Kampagne: alle tragenden Annahmen gegen Echtdaten verifizieren.
3. **SP0–SP6** — inkrementeller Rewrite, je Sub-Projekt Feature-Branch → Plan → PR.

**Harness:** volle ortus-Parity **außer Last-Test-Stack**, **OTel von Tag 1**, plus **Debug-MCP** (Logs+Spans für Claude Code), plus `claude-skills`-Submodul.

## 1. Grundprinzipien (nicht verhandelbar)

Aus Teil A des Quelldokuments, als Architektur-Invarianten:

### A.1 Drei Ebenen, strikt getrennt

| Ebene | Frage | Anker | Tabellen |
|---|---|---|---|
| **Nomenklatur** | Wie heißt der Name, wer publizierte ihn? | IPNI-ID | `name` |
| **Taxonomie (Konzept)** | Welche Individuen umfasst das Taxon? | Backbone-ID + Version + `sec.` | `taxon_concept`, `concept_name` |
| **Merkmal** | Welche Traits hängen daran? | Trait-Vokabular + Version | `trait_value` |

Diese drei dürfen **nie** in einer Tabelle liegen. Sonst lässt sich nicht ausdrücken, dass *Festuca ovina* sec. Euro+Med etwas anderes umfasst als sec. WCVP.

### A.3 Late Binding — die eiserne Regel

Verbatim-Name ist Primärdatum; die Auflösung (`resolution`) ist derivativ und jederzeit neu berechenbar. **Gilt hier für den Ingest:** Backbone-Artefakte sind immutable und versioniert; ein Backbone-Wechsel ist ein Re-Ingest, keine Migration. (Das `plant_record`-Late-Binding lebt im Consumer, nicht in hostus — aber hostus muss die Auflösung reproduzierbar und versioniert liefern, damit der Consumer sie wegwerfen und neu anfragen kann.)

### Versionierung

**Versionen immer pinnen, nie „latest".** Der GermanSL-Changelog dokumentiert, dass IDs zwischen Versionen gelöscht/neu zugeordnet werden. Jede Artefakt-Identität kodiert die Version/Periode im `id`.

## 2. Phase R — Recherche & Quellenvalidierung

**Ziel:** Für jede Datenquelle *vor* jedem PoC klären: beziehbar? lizenziert? Format? Zugriff? Version/Periode?

**Werkzeug:** `deep-research`-Skill (Fan-out-Suche → Quellen laden → adversariale Prüfung → zitierter Bericht).

**Deliverable:** `docs/research/quellenregister.md` — validierte Tabelle:

| Spalte | Inhalt |
|---|---|
| Quelle | z. B. „WCVP ColDP" |
| URL | Download-/API-Endpoint (gepinnt) |
| Lizenz | z. B. CC-BY-4.0 + Attribution |
| Format | ColDP / TSV / SPARQL / REST-JSON |
| Zugriff/Auth | offen / API-Key / Genehmigung |
| Version/Periode | z. B. 2026-06-15 |
| Status | ✅ validiert / ⚠️ Größenordnung / ❌ blockiert |

**Abzudecken:** COL XR (checklistKey `7ddf754f-d193-4cc9-b351-99906754a03b`), WCVP/POWO, Euro+Med (ColDP/CDM), FloraVeg.EU/ESy, EIVE 1.0 (Dengler et al. 2023), Tichý et al. 2023, Midolo 2023, GermanSL, EuroSL, Wikidata-Properties (P14607/P846/P10585/P12380/P12100), iNaturalist-API, PlantNet-API, TaxRef/Bayernstatus, ASK/FIN-Web, Wisskirchen/CDM-Portal (`portal.cybertaxonomy.org/rotelisten_flora_deutschland`), IPNI/WFO.

**Startliste:** der Anhang „Quellenlage" des Quelldokuments. Jede ✅-Zeile wird gegen die Primärquelle re-validiert (nicht blind übernommen), jede `‹auflösen›`/⚠️-Zeile wird ermittelt.

**Gate:** Eine ❌-Quelle (nicht beziehbar / Lizenz inkompatibel) blockiert das SP, das sie braucht — dokumentiert, nicht stillschweigend umgangen.

## 4. Zielarchitektur

### 4.1 Architekturstil

Hexagonal (Ports & Adapters), wie ortus:

```
internal/
  domain/        # reine Domäne: Name, Concept, Trait, Xref, Distribution, Relation. Keine I/O-Deps.
  application/   # Use Cases: Suggest, Match, ResolveConcept, ReverseXref, Traits, Synonyms, Translate, Ingest, Bundle
  ports/
    input/       # Interfaces, die die Application anbietet
    output/       # Interfaces, die die Application braucht (Repository, TraitStore, ...)
  adapters/
    sqlite/      # SQLite/FTS5-Repository (modernc.org/sqlite)
    coldp/       # ColDP-Importer
    http/        # gorilla/mux-Router + Handler + Middleware-Kette
    mcp/         # Debug-MCP (stdio) — Logs+Spans
    telemetry/   # OTel-Setup (Traces+Metrics), slog-span-Handler
    bundle/      # Offline-Bundle-Export (gefilterte SQLite-Kopie)
  app/           # Composition-Root (Wiring)
  config/        # viper
```

Hexagon-Grenzen werden durch `depguard`/`gomodguard` im Linter erzwungen (aus ortus übernommen).

### 4.2 Domänenmodell — die drei Ebenen

- `Name` — nomenklatorische Identität. Felder: canonical, authorship, rank, `ipni_id`, `published_in`, nomenklatorischer Status (`nom. nud.`, `nom. superfl.`, `pro syn.`, …), basionym-Verweis.
- `Concept` — taxonomisches Konzept. Felder: `backbone_id`, `backbone_version`, `sec_reference`, accepted-Name-Verweis, Rang, Klassifikation (parent).
- `Trait` — Merkmalswert. Felder: `concept_id`, `vocab`, `vocab_version`, Dimensionen (M/N/R/L/T [+ Salinität bei Tichý]), Nischenbreite (nur EIVE), `n_systems`.

### 4.3 Storage-Schema (SQLite/FTS5, `modernc.org/sqlite`)

Ein Schema, serverseitig und im Bundle identisch (Bundle = gefilterte Kopie + `snapshot_version`).

```sql
-- Artefakt-/Versionsmetadaten
CREATE TABLE backbone_version (
  id            TEXT PRIMARY KEY,   -- z.B. "wcvp"
  version       TEXT NOT NULL,      -- "2026-06-15" (Periode/Version, nie "latest")
  license       TEXT,
  source_url    TEXT,
  ingested_at   TEXT NOT NULL,
  manifest_sha  TEXT NOT NULL       -- Checksumme des validierten Manifests
);

-- Nomenklatur
CREATE TABLE name (
  id            TEXT PRIMARY KEY,
  canonical     TEXT NOT NULL,
  authorship    TEXT,
  rank          TEXT NOT NULL,      -- FAMILY|GENUS|SPECIES|SUBSPECIES|VARIETY|FORM
  ipni_id       TEXT,
  published_in  TEXT,
  nom_status    TEXT,               -- NULL|nom_nud|nom_superfl|pro_syn|...
  basionym_id   TEXT REFERENCES name(id)
);

-- Taxonomie
CREATE TABLE taxon_concept (
  id             TEXT PRIMARY KEY,
  backbone_id    TEXT NOT NULL REFERENCES backbone_version(id),
  accepted_name  TEXT NOT NULL REFERENCES name(id),
  rank           TEXT NOT NULL,
  parent_id      TEXT REFERENCES taxon_concept(id),
  sec_reference  TEXT,              -- bibliografische sec.-Identität
  status         TEXT NOT NULL      -- accepted|...
);

-- Konzept <-> Name (accepted + Synonyme, mit Typisierung)
CREATE TABLE concept_name (
  concept_id   TEXT NOT NULL REFERENCES taxon_concept(id),
  name_id      TEXT NOT NULL REFERENCES name(id),
  role         TEXT NOT NULL,       -- accepted|synonym
  homotypic    INTEGER,             -- 1=homotypisch (Basionym/Rekombination), 0=heterotypisch
  PRIMARY KEY (concept_id, name_id)
);

-- Cross-References zu Fremdautoritäten
CREATE TABLE xref (
  concept_id   TEXT NOT NULL REFERENCES taxon_concept(id),
  authority    TEXT NOT NULL,       -- powo|colxr|euromed|gbif|wikidata|wfo|inat|floraveg
  ext_id       TEXT NOT NULL,
  PRIMARY KEY (authority, ext_id)
);

-- Volkssprachliche Namen (deutsch nach Buttler et al. 2018 o.ä.)
CREATE TABLE vernacular (
  concept_id   TEXT NOT NULL REFERENCES taxon_concept(id),
  lang         TEXT NOT NULL,       -- de|en|...
  name         TEXT NOT NULL,
  preferred    INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (concept_id, lang, name)
);

-- Verbreitung (Bezugsraum-Ranking)
CREATE TABLE distribution (
  concept_id   TEXT NOT NULL REFERENCES taxon_concept(id),
  area_scheme  TEXT NOT NULL,       -- wgsrpd_l3|euromed|bayern
  area_code    TEXT NOT NULL,
  PRIMARY KEY (concept_id, area_scheme, area_code)
);

-- Zeigerwerte/Traits (Zeiger auf Konzept + Vokabularversion, nicht die Zahlen als Wahrheit)
CREATE TABLE trait_value (
  concept_id    TEXT NOT NULL REFERENCES taxon_concept(id),
  vocab         TEXT NOT NULL,      -- eive|tichy2023|midolo2023
  vocab_version TEXT NOT NULL,
  dim           TEXT NOT NULL,      -- M|N|R|L|T|S
  value         REAL,
  niche_width   REAL,               -- nur EIVE
  n_systems     INTEGER,
  PRIMARY KEY (concept_id, vocab, vocab_version, dim)
);

-- Konzeptbeziehungen (UC6)
CREATE TABLE concept_relation (
  from_concept  TEXT NOT NULL REFERENCES taxon_concept(id),
  to_concept    TEXT NOT NULL REFERENCES taxon_concept(id),
  relation      TEXT NOT NULL,      -- congruent|includes|included_in|overlaps|disjoint
  source        TEXT,               -- z.B. wisskirchen-1998
  PRIMARY KEY (from_concept, to_concept, source)
);

-- Volltext/Prefix-Suche
CREATE VIRTUAL TABLE fts_name USING fts5(
  canonical, vernacular_de,
  content='',                       -- externer Content, IDs über rowid-Mapping
  tokenize='unicode61 remove_diacritics 2'
);
```

`aggregate_policy` (UC4) und `sec_inference` (UC3) werden als abgeleitete Felder bzw. Response-Strukturen geliefert, nicht als eigene Tabellen persistiert (sie sind Interpretationen, keine Backbone-Fakten).

### 4.4 Artefaktvertrag (ortus-Muster)

- **Fixed-Name-Manifest** je Backbone-Bundle, validiert gegen ein **im Binary eingebettetes JSON-Schema** (JSON Schema 2020-12), doppelt gate-t: Pipeline validiert beim Bauen, hostus re-validiert beim Ingest mit `KnownFields(true)` (unbekannte Felder → Fehler). Manifest-Name: **`dataset.yaml`** (wie im Quelldokument D.2 genannt; enthält `backbones:` und `trait_vocabularies:` mit gepinnten Versionen/Lizenzen).
- **Immutable Identity:** `id` kodiert Version/Periode, nie „latest"; Bundle-Dateiname-Stamm == `id`.
- **Reproduzierbare Pipeline je Backbone:** `pipelines/<backbone>/build.sh` (`set -euo pipefail`, gepinnte Download-URL → normalisieren → SQLite/ZIP erzeugen → gegen Schema validieren). Kein „latest"-Zug.
- **Checksumme:** `manifest_sha` in `backbone_version` bindet den Ingest an das exakt validierte Manifest.

### 4.5 API-Oberfläche (Teil B des Quelldokuments)

| Endpunkt | Zweck | SP |
|---|---|---|
| `GET /v1/suggest` | Autosuggest, bezugsraum-gerankt | SP2 |
| `POST /v1/match` | Batch-Namensauflösung (Verbatim → Konzeptkandidaten) | SP1 (exact/exact_author), SP3 (fuzzy) |
| `GET /v1/concept/{id}` | Konzept mit Xrefs + Klassifikation | SP1 |
| `GET /v1/xref` | Reverse-Lookup Fremd-ID → Konzept | SP1 (Basis), SP4 (Anreicherung) |
| `GET /v1/concept/{id}/traits` | Zeigerwerte pro Vokabular | SP3 |
| `GET /v1/concept/{id}/synonyms` | Synonymliste, relevanzfilterbar | SP6 |
| `POST /v1/translate` | Konzeptübersetzung zwischen `sec.`-Räumen | SP5 |
| `GET /openapi`, `GET /metrics`, `GET /health/{live,ready}` | Betrieb | SP0 |

**Ranking `/v1/suggest`** (Priorität, Teil B.1): 1. Präfixtreffer Gattung/Art → 2. `in_area` → 3. accepted vor Synonym → 4. Rang (Art→Unterart→Varietät) → 5. String-Score (Tiebreaker).

**`/v1/match`:** Fuzzy-Treffer setzen zwingend `requires_review: true` (Teil B.2).

**Offline-Bundle:** SQLite/FTS5, gefiltert auf `in_area` für einen Bezugsraum, ~10–20 MB Mitteleuropa, delta-synchronisiert über Versionsnummer, inkl. Trait-Snapshot (klar als `snapshot_version` markiert).

### 4.6 HTTP-Middleware-Kette (Reihenfolge aus CLAUDE.md, + OTel)

Request-ID → Logging → Rate-Limiting → Load-Shedding → Timeouts → CORS → Metrics, durchgängig OTel-instrumentiert (otelmux). Aus dem PoC-Code übernommen: bestehende Middleware-Implementierungen werden portiert.

### 4.7 Fehlerformat

Format aus CLAUDE.md beibehalten:
```json
{ "error": { "code": "ERROR_CODE", "message": "Human readable message" } }
```
Codes: bestehende (`INVALID_QUERY`, `RATE_LIMIT_EXCEEDED`, `UPSTREAM_OVERLOADED`, `GBIF_TIMEOUT`, `GBIF_UNAVAILABLE`, `INTERNAL_ERROR`) **+ neu** `NOT_FOUND`, `UNRESOLVABLE`. GBIF-spezifische Codes bleiben nur, solange GBIF `/v2/match` als Ingest-/Anreicherungspfad genutzt wird.

### 4.8 CLI (cobra + viper)

- Root = `serve` (Default).
- `hostus ingest --dataset dataset.yaml` — Backbone-Import.
- `hostus validate --dataset dataset.yaml` — Manifest gegen Schema prüfen, ohne Import.
- `hostus bundle --area DE-BY --out bundle.sqlite` — Offline-Bundle exportieren.
- `hostus mcp` — Debug-MCP (stdio, siehe 5.3).
- `hostus version`.

Config: viper mit Prefix `HOSTUS_`, `.` → `_` Replacer; Präzedenz `.env` < Env < CLI (CLAUDE.md).

## 6. Rewrite-Mechanik

- **In-place ausweiden**, kein neues Repo. Git-Historie bleibt. Modulpfad `github.com/jobrunner/hostus` bleibt. Version → **`v2.0.0`**.
- **Behalten (portieren):** Middleware-Implementierungen, config-Muster (viper), httperr (Codes erweitern), OpenAPI-from-code, Makefile/CI/Docker/Nix-Gerüst als Ausgangsbasis.
- **Entfernen:** `internal/gbif`, `internal/taxonomy` (GBIF-spezifischer Mapper), GBIF-gestützter `suggest`-Handler.
- **ADRs:** ADR-001 (GBIF alleiniger Provider), ADR-003 (kein Persistenz-Layer), ADR-008 (keine Persistenz) werden **superseded** durch neue ADRs (lokaler Multi-Backbone-Index, SQLite/FTS5-Persistenz, Artefaktvertrag, hexagonal, OTel, Debug-MCP). Alte ADRs bleiben als „Superseded" erhalten.
- Jedes SP = eigener Feature-Branch → Implementierungsplan → PR. VERSION + CHANGELOG in jedem PR (CLAUDE.md/CI-Regel).

## 8. Nicht-Ziele (Scope-Grenzen)

- Kein `plant_record`-Schreibpfad, kein System-of-Record für Erfassungen (Consumer-Sache).
- Kein RDF-Knowledge-Graph in hostus (UC3-KG ist Consumer; hostus liefert nur `match` + `sec_inference`).
